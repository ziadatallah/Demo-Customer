Connecting your requirements tool

Everything you and your tool administrator have to do so ISAF can read requirements straight out of your requirements tool, instead of exporting files by hand. Applies from ISAF v5.3.29.

What ISAF does, and what it never does

Your requirements tool
Jama Connect, Polarion, DOORS or another tool, on your own network or your own cloud tenancy.
→
Your ISAF app
Reads the requirements, reviews them, and puts them into your documents.
→
Your reviewer
Completes and signs the review. ISAF eases the manual work; it does not replace the review.
  • It only reads. ISAF never creates, changes or deletes anything in your requirements tool.
  • Your credentials stay with you. They are entered into your own ISAF app and kept by that server. They are never sent to MX Aero, and once saved the app never shows them again.
  • Your requirements stay with you. They are read into your app for the review and the documents. Nothing is sent to MX Aero.
  • You need your own licence for the connected tool, and a user account that may read the project.
Hosted ISAF sites: if MX Aero hosts your ISAF site, anything you type into it sits on that hosted service, and its disk is temporary, so a saved connection is lost when the site restarts. For a connected requirements tool, use ISAF installed on your own server, and have your administrator set the credentials as environment variables (named under each tool below) rather than typing them into the page.

Your ISAF app shows only what is on your licence. If a tool below is missing from your Import tab, or the file import is, it is not enabled for your company: ask MX Aero to add it. With no requirements import on the licence there is no Import tab at all.

A tool with no live connection is not a lesser route: ISAF reviews an exported file exactly as it reviews a live pull, and the same findings, checklist evidence and document updates come out. The live connection only saves the export step.

Polarion (Siemens)

What to ask your Polarion administrator for

  1. The REST address. Your Polarion site followed by /polarion/rest/v1, for example https://polarion.yourcompany.com/polarion/rest/v1. Typing just the site address also works; ISAF adds the rest.
  2. That the REST API is switched on for your site and reachable from the server ISAF runs on. A Polarion inside the company network can only be reached by an ISAF installed inside that network.
  3. A user account that may read the project you want to import.

What you do

  1. In Polarion, open My Account → Personal Access Tokens and create a token. Copy it at once: Polarion shows it once. Note its expiry date — tokens expire and must be renewed, and the import stops working when one does.
  2. In ISAF, open the Import tab → Read requirements straight from Polarion → Polarion connection settings. Enter a name, the REST address and the token, then Save connection.
  3. Test connection. ISAF reports how many projects the token can see.
  4. Load projects, choose the project, and tick the work item types that hold requirements or test cases. ISAF finds the types by reading a sample of the project, with how many of each it saw.
  5. Optionally add an extra search in Polarion's own syntax, for example status:approved AND severity:must_have, to read only part of a type.
  6. Read requirements. Each work item type becomes a card. Check the level and the columns, then run the review as usual.

What ISAF reads

  • Work items of the chosen types, with their fields and custom fields as columns, and rich text turned into plain text.
  • The work item ID (VC-12) as the requirement ID, and the outline number as the position in the specification.
  • The links between work items, with their role, as the trace links. Links to another project and links Polarion marks suspect are kept and marked.

Set as environment variables instead of typing them in: ISAF_POLARION_URL and ISAF_POLARION_TOKEN.

Jama Connect (Jama Software)

What to ask your Jama administrator for

  1. The REST address. Jama Cloud uses https://yourcompany.jamacloud.com/rest/v1. A Jama you host yourself often uses https://yourhost/contour/rest/v1.
  2. An API client, if your Jama licence allows it (API access is a licensed feature in some Jama plans), and that the API client's user may read the project.

What you do

  1. In Jama, open your user profile → Set API Credentials and create a client. Copy the client ID and the client secret at once: Jama shows the secret once.
  2. In ISAF, open the Import tab → Read requirements straight from Jama Connect → Jama Connect connection settings. Enter a name, the address and the client ID and secret, then Save connection.
  3. Test connection, then Load projects, choose the project, and tick the item types that hold requirements or verification cases. Folders and sets can be left out.
  4. Read requirements, check the level and columns on each card, and run the review.

A user name and password work instead of an API client, but Jama refuses them on sites with single sign-on, so the API client is the reliable route.

What ISAF reads

  • Items of the chosen item types, with the Jama field labels as the columns, pick-list fields shown by their value ("Analysis", not a number), and rich text turned into plain text.
  • The document key (VC-SYS-12) as the requirement ID.
  • The relationships of the project, with their type name, as the trace links; suspect links are marked.

Set as environment variables instead of typing them in: ISAF_JAMA_URL, ISAF_JAMA_CLIENT_ID and ISAF_JAMA_CLIENT_SECRET (or ISAF_JAMA_USERNAME and ISAF_JAMA_PASSWORD).

Preparing an Excel or CSV file

There is no ISAF template to fill in: ISAF reads the file you already have. Download an example file to see the shape, or compare it with your own export.

How the file is read

  • Excel (.xlsx, .xlsm): the sheet with the most rows is used. If your workbook has several sheets of requirements, export or save one sheet per import.
  • The header row is found automatically: the first row with at least two filled cells. A title block, a logo or notes above the table are skipped.
  • CSV (.csv, .txt): comma, semicolon and tab separated files are all read, as is the UTF-8 that Excel writes, so a European semicolon export needs no conversion.
  • Empty rows are ignored, two columns with the same name are numbered apart, and at most 50,000 rows are read from one file.
  • Merged cells, colours, filters and formulas are irrelevant: ISAF reads the values.

What the columns must contain

Two columns are needed. Everything else is optional and only adds checks, so start with what you have.

ColumnNeeded?What it gives you
IDRequiredThe identifier a reviewer and the documents use, for example VC-SYS-12.
Requirement textRequiredThe requirement itself. Wording, ambiguous and open terms (TBD, TBC, TBR), units, tolerances and length are checked against it.
Traces to (parent IDs)OptionalThe trace: coverage per level, broken links, requirements not traced and parents not developed further. Excel and CSV carry no links of their own, so without this column there is no trace. Several parents in one cell, separated by a comma or a semicolon, are fine.
Derived, RationaleOptionalA derived requirement without a rationale is reported; a derived system requirement is also checked for validation and safety review.
Verification methodOptionalRequirements with no verification method, and the test coverage per level.
Validation method, Validation conclusionOptionalThe system-level validation checks (ARP4754A).
Assumption, Safety related, DAL, SourceOptionalAssumptions recorded, safety requirements without a DAL, an invalid DAL, and system requirements with no identified source.
Title, HeadingOptionalA heading row is recognised as a heading and not reviewed as a requirement.
ItemOptionalThe software or hardware item each requirement belongs to, when one module covers several. ISAF puts each requirement in that item’s documents. Without this column every row takes the Item set on the file card. An item that is not in your program is reported as an error rather than dropped, because its requirements would otherwise reach no document.

Column names

Name them however your process names them. ISAF suggests the mapping and you correct it on the card before running the review; the choice is remembered for the next file with the same columns. Names it recognises on its own include:

  • ID: ID, Req ID, Requirement ID, Identifier, Key, Document Key, Absolute Number, Object Identifier
  • Requirement text: Requirement Text, Object Text, Requirement, Statement, Text, Description
  • Traces to: Traces To, Trace To, Parent, Parent ID, Parent Requirement, Satisfies, Derived From, Upstream
  • Verification: Verification, Verification Method, Test Method, VM
  • Others: Derived, Rationale, Justification, Validation Method, Validation Status, Assumption, Safety, Safety Related, DAL, FDAL, IDAL, Source, Origin, Title, Name, Heading
  • Item: Item, LRU, Unit, Software Item, Hardware Item, Subsystem, Component, Equipment, Allocated To, Allocation, Applies To, Assigned To, Module

One file per level

Each file you add is given a level: system requirements, software high-level, software low-level, hardware requirements or verification cases. The level decides which standard the findings cite (DO-178C, DO-254, ARP4754A / ARP4761A) and how the trace is built between files, so export one level per file. If one file holds several levels, add a column saying which, and map it as the optional object type.

DOORS, DOORS Next and every other tool

There is no live connection to these yet. The route today is an export, and it loses nothing that matters to the review:

  1. DOORS Next: open the module or collection, then Export → ReqIF, which produces a .reqif or .reqifz file. DOORS 9.x: use the ReqIF export in the DOORS client, or export to Excel.
  2. Keep the attributes you want ISAF to see in the export: the identifier, the requirement text, the trace or link column, and whatever you use for verification method, derived, rationale, safety and DAL.
  3. In ISAF, Import tab → Add requirements files…, then set the level and check the columns on each card.

ReqIF keeps the links between modules, so the trace is built from the export just as it is from a live connection. Excel and CSV have no links, so add a column of parent IDs and map it to Traces to.

If you would like a live connection to DOORS Next or another tool, tell MX Aero which tool and version you use. Each tool is a separate piece of work, and it needs access to an instance of yours to build and test against.

When something does not work

What you seeWhat it usually means
"refused the personal access token" (Polarion)The token has expired or was revoked. Create a new one in My Account → Personal Access Tokens and save it again.
"refused the API client ID or secret" (Jama)The client ID or secret is wrong, or the API client was removed. Create new credentials in the Jama user profile.
"single sign-on" mentioned in a Jama messageThe site uses single sign-on, so a user name and password will never work. Use an API client ID and secret.
"accepted the token but the user may not read this project"The account is fine but has no read access to that project. Ask your tool administrator for it.
"could not reach" the toolThe ISAF server cannot see the tool: usually a tool inside the company network and an ISAF outside it, a firewall, or a VPN that the ISAF server is not on.
The tool sees no projectThe account can sign in but sees nothing. Ask for read access to the project.
The import takes several minutesNormal for a large project: both tools limit how fast they answer, and ISAF waits rather than hammering them. Leave the tab open.
"Not every item was read"The project is larger than one import (20,000 items). Narrow it with the extra search, or import one type at a time.
A column you need is missingTools only return a field that holds a value. If a field is empty everywhere it still appears in the column list and can be chosen by hand.
No trace links came throughIn Polarion, check that work items really are linked rather than only sharing a document. In Jama, check that the relationships exist in the project. For file imports, map the Traces to column.

Before you connect: a short checklist

  • Your own licence for the tool, and a user account that may read the project.
  • ISAF installed where it can reach the tool (same network, or a route to it).
  • Credentials created, and the person who will renew them when they expire.
  • Agreement on which item or work item types hold requirements, and which fields mean verification method, derived, rationale, safety and DAL.
  • A note in your plans (PSAC, SDP, PHAC or equivalent) of where the requirements come from and how they reach the documents, since the authority will ask.

An import is an aid, not a review and not a qualified tool: the findings help the reviewer, who still performs, completes and signs the review.
